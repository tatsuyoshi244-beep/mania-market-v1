# 作業前後の確認手順

## 必須ルール

1. 作業前に、GitHub `main`、Vercel本番コミット、対象コードの3点を照合する。
2. 外部サービスが発行したURLや環境変数は、根拠なく削除・補完・正規化しない。
3. 修正後は、型検査・Lint・本番ビルドだけで完了扱いにしない。
4. Vercel本番の `/api/health` でDBとAuthがともに `ok`、かつ想定コミットが稼働していることを確認する。
5. 認証変更は、画面表示、Auth到達性、登録・ログインの順に確認する。利用者に同じ操作を繰り返させない。

## 障害調査の工程

1. 事象を「画面・アプリ処理・外部認証・環境変数・DB・デプロイ」の層に分け、原因候補を先に一覧化する。
2. 発生確率と影響度で優先順位を付ける。複数の読み取り確認は並行して行う。
3. ログ、HTTPステータス、エラーコード、稼働コミットを証拠として残し、推測だけで設定を変更しない。
4. 一つの変更ごとに仮説と期待結果を定義し、外れた場合は元に戻すか差分を明示する。
5. 修正後は正常系だけでなく、入力不備、登録済み、許可元拒否、レート制限、外部サービス停止を確認する。
6. 完了条件は「利用者画面が開く」ではなく、ブラウザ → Server Action → Neon Auth → DB → 応答の一連が成功することとする。

### 認証障害の優先確認表

| 優先 | 原因候補 | 同時に確認する証拠 | 判定方法 |
| --- | --- | --- | --- |
| 1 | 稼働コミット・重複デプロイの不一致 | GitHub `main`、Vercel SHA、アクセス中ホスト | 3点が一致する |
| 2 | Auth URL・環境変数の欠落/誤り | `/api/health`、Vercel Production変数 | DB/Authが設定・到達可能 |
| 3 | Trusted Origins拒否 | `/api/health/auth`、Authのエラーコード | `origin_accepted`。`INVALID_ORIGIN`ではない |
| 4 | SDK・Server Actionの例外処理 | Runtime Log、画面のエラー分類 | 構造化コードが画面分類に保持される |
| 5 | ユーザー固有問題 | 登録済み、資格情報、role、public.users同期 | 別層が正常と確認後に調べる |

認証変更の公開後は `npm run auth:check` で、副作用のないログイン失敗リクエストを使って本番Originの許可状態を確認する。

## 管理者権限の初期同期

- Neon Authでのログイン成功と、アプリDBの`public.users.role`は別の状態として確認する。
- オーナー管理者は平文メールではなくSHA-256ハッシュで照合する。
- `/admin`への初回アクセス時に`ensureAppUser`を実行し、オーナーだけを`admin`へ同期する。
- オーナー以外の既存roleは変更しない。管理者権限を一般ユーザーへ自動付与しない。
- 管理者ログインの完了条件は、認証成功だけでなく`/admin`の内容表示と管理APIの権限確認までとする。

## 2026-09-13 Neon Auth障害

- 事象: 新規登録が「登録処理に接続できませんでした」で失敗した。
- 原因: NeonのProject Infoが発行した完全なAuth URLから、必要な末尾パスをコード側で削除した。
- 修正: `NEON_AUTH_BASE_URL` は末尾の `/` だけを除き、それ以外のパスはそのままSDKへ渡す。
- 再発防止: `/api/health` は環境変数の有無だけでなく、Neon Authの `get-session` へ実際に到達できるかを確認する。

## 2026-09-15 登録・ログイン障害

- 事象: 出店者の新規登録と管理者ログインがどちらも失敗した。
- 直接原因: Neon Authの信頼済みドメインが空で、本番オリジンからの認証要求が `403 INVALID_ORIGIN` で拒否されていた。
- 修正: Neon Consoleのmainブランチで `https://mania-market-v1.vercel.app` を信頼済みドメインに登録した。
- 確認: 本番のログインAPIが `INVALID_ORIGIN` ではなく通常の認証結果を返し、登録APIも通常の入力検証まで到達することを確認した。
- 併発事項: 同じGitHubリポジトリが `mania-market-v1` と `mania-market-v1-7nnf` の2つへデプロイされていた。後者はDB/Auth環境変数が未設定。
- 再発防止: 未設定の複製ドメインへのアクセスは `proxy.ts` で正常な本番ドメインへ恒久転送する。公開・QR・営業素材には正常な本番URLだけを使用する。
